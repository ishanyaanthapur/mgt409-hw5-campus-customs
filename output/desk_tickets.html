Reflection — Problem 10

Written by Ishanya Anthapur about the Problem 9 run on 2026-10-13 (audit events #469–#587). Evidence: Ticket 101 · Ticket 102 · Ticket 103 · Cash · output/resolved_tickets.json · output/resolved_board.html

1How would you evaluate the agents' performance on each ticket, and why?

Ticket #101

Strong performance

Agent performance was strong on this ticket. The Boss called Inventory, which was then able to call Accounting directly rather than going back through the Boss. I regard this as good performance because it avoided an extra handoff through the Boss. The agent activity runtimes were 45 seconds and 27 seconds, and the agents proposed an $840 payment for human approval. They waited for my approval before proceeding with Inventory and Customer Service. One minor flaw was that the customer service draft was signed with a made-up shop name, “Campus Corner Shop.”

Ticket #102

Cleanest performance

This ticket had the cleanest performance. The Boss called Facilities, and Facilities called Accounting when needed. Facilities followed its instructions and did not prepare the payment itself. Inventory and Customer Service were correctly left out because they were not needed. Resolving this ticket took 26 seconds of agent activity.

Ticket #103

Weakest performance

This ticket had the weakest performance and took four runs to resolve. The process stalled mainly because the Boss invented a rule requiring human approval for a discount. While I liked the idea of an approval step, the agent never sent the request to the approval queue, so I had no way to approve it and move the process forward. Customer Service also described the discount as “not yet confirmed,” contributing to the coordination issue. I had to use Claude to diagnose the problem and fix the agent prompts before I could successfully close the ticket.

There were some positives. Inventory proposed a 20% discount that kept the selling price above the unit cost, resulting in $24.40 profit per hoodie. The team also correctly skipped Accounting because ticket #101 had already cleared invoice #501.

Customer Service signed its draft “Campus Creations,” which was different from the made-up name it used previously. This made me realize that I need to give the Customer Service agent explicit guidance on using a standard signature and the correct shop name. The recorded agent activity runtime was 71 seconds.

2For each ticket, how did Actual compare with the Expected plan?

Ticket #101

The plan had the Boss delegate to Accounting; in reality, Inventory did so directly. This was a positive difference because it avoided an extra loop back to the Boss. The plan also expected a new restock, but there was none in the actual run, which avoided an additional step. Finally, the plan anticipated one run that would pause for approval. In reality, it took two runs because the prepare-then-approve design was introduced after the plan was written.

Ticket #102

The actual run was nearly an exact match with the plan. One difference was that Accounting saw $2,560 rather than $3,400 in checking because the payment for ticket #101 had already been made before we started resolving #102. Also, the backend marked the ticket as resolved rather than the Boss.

Ticket #103

The plan’s conditional “pay invoice #501 first” step was correctly skipped because the invoice had already been paid. The plan expected the agent to ask the customer for a discount percentage. In the actual run, Inventory proposed a concrete 20% discount, which we then offered to the customer. I think this was better because the agent ensured that we would still make a profit on the hoodies. However, it took four runs instead of one because of the invented approval rule and an approval that arrived mid-run.

3What would have been simpler with one agent using tools, and why?

Ticket #102 would have been simpler with one agent because it just needed to check the bill, check available cash, and prepare a payment for my approval. Passing it from Boss to Facilities to Accounting worked well, but felt unnecessary for a straightforward task.

For #103, since there were so many agents called and multiple runs, one agent that could handle more tasks might have made resolving this ticket more effective. One agent could have checked stock, calculated the discount, and drafted the customer response. This may have avoided the back-and-forth over whether the discount was confirmed or needed approval. One agent could still make up a rule, though bc AI is non-deterministic, so I’d still need clearer prompts- like if you make a rule please ensure all the next steps are implemented too (like sending the request up to be approved).

4Three new problems Campus Customs could solve with the agents and tools we built

Problem 1

We could handle restocking → when a customer orders something and we don’t have enough inventory, the agents can propose a restock order for the shortfall for my approval. This is what happened on ticket #103, where Inventory found only 8 of the 20 hoodies and proposed ordering the other 12.

Problem 2

We could facilitate all our supplier or vendor payments (rent, printers, etc), like next month’s rent (due 2026-10-02) or Bulldog Print Co’s invoice for the 12 hoodies once it arrives.

Problem 3

We can decline to pay a bill when our checking account balance is too low; for example, the ~$264 hoodie invoice would be refused because only $160 is left in checking. However, I would probably need to add a guardrail so that a human is notified of this immediately.

5Three new problems it could not solve with the current tools — and the tools and agents it would need

Problem 1

Not enough cash: When the checking balance is below the invoice amount, the payment tool refuses the payment when I click Approve, but the agents can’t resolve the shortfall. A new Treasury agent, working alongside Accounting, would need tools like request_funding to ask a human for more funds or request_payment_extension to ask the vendor for more time.

Problem 2

Recording revenue: If the Yale AI Club pays $928 for their hoodies, we don’t record that revenue anywhere. A new Sales agent would need record_sale and collect_payment tools to record the sale and process payment, updating the cash balance once payment is confirmed.

Problem 3

Sending customer messages: The agents can draft messages but can’t actually send them. A new Communications agent, taking finished drafts from Customer Service, would need request_message_approval and send_message tools so a human can review and approve the message before it is sent.
